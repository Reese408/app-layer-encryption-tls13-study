# Architecture

## 1. Overview

```
                         Docker Compose network (bridge)
 ┌────────────┐  TLS 1.3   ┌───────────────────────────────┐
 │            │──────────▶│ api-plain   (ENCRYPTION=off)    │──┐
 │  k6 load   │           │  FastAPI + Uvicorn, 1 worker   │  │  optional (Phase 4)
 │ generator  │  TLS 1.3   ├───────────────────────────────┤  ├──────────────────▶ Ollama (host)
 │ (grafana/  │──────────▶│ api-aead    (ENCRYPTION=aesgcm)│──┘   host.docker.internal:11434
 │   k6)      │           │  same image, same workload     │       qwen3:8b
 └────────────┘           └───────────────────────────────┘
        │                              │
        ▼                              ▼
 results/raw/<ts>/k6-*.json     results/raw/<ts>/resources.csv   ◀── scripts/sample_resources.py
                                                                    (docker stats, 1 Hz)
```

Both API services are built from **one image**. The only configuration difference is `ENCRYPTION_MODE`. Each service has the same CPU and memory limits, the same TLS certificate, and the same single Uvicorn worker.

Ollama runs natively on the macOS host rather than in a container, so it can use Metal GPU acceleration. Both API services reach it at the same address with the same settings.

## 2. Request pipeline

```
plain:  TLS ─▶ JSON parse ─▶ workload(plaintext) ─▶ JSON serialize ─▶ TLS
aead:   TLS ─▶ envelope parse ─▶ AES-GCM open ─▶ JSON parse ─▶ workload(plaintext)
                ─▶ JSON serialize ─▶ AES-GCM seal ─▶ envelope serialize ─▶ TLS
```

The workload step is the **same function, called with the same plaintext bytes** in both modes. Middleware times each stage and reports it in a `Server-Timing` response header, for example `dec;dur=0.04, work;dur=1.20, enc;dur=0.03`. This makes it possible to separate cryptographic cost from total latency.

## 3. Endpoints (planned)

| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Liveness check. Returns mode and key ID only, never key material. |
| POST | `/v1/process` | Deterministic workload: canonicalize the JSON payload, compute a fixed number of SHA-256 rounds over it, and return the digest along with an echo of the payload. The cost scales with payload size and is identical in both modes. |
| POST | `/v1/infer` | Phase 4. The plaintext body is `{"id", "prompt", "max_tokens"}`. The route forwards the prompt to Ollama with fixed generation options (research-design.md §7.1) and returns `{"id", "response", "meta"}`, where `meta` holds Ollama's token counts and durations. In aead mode both bodies are sealed exactly as on `/v1/process`. `Server-Timing` reports `dec`, `infer` (the wall time of the Ollama call), `enc` and `app`. |

## 4. Encryption envelope (aead mode)

The request and response bodies are `application/json`:

```json
{ "v": 1, "kid": "k2026-10-a", "n": "<base64url 12-byte nonce>", "ct": "<base64url ciphertext||tag>" }
```

- **Algorithm:** AES-256-GCM with a 128-bit tag, using `cryptography.hazmat.primitives.ciphers.aead.AESGCM`.
- **Nonce:** 96 random bits per message (`os.urandom(12)`).
- **AAD:** `"v1|" + direction + "|" + METHOD + "|" + path + "|" + kid`, where direction is `c2s` or `s2c`. This stops a ciphertext from being replayed to a different route or reflected back as a response.
- **Keys:** two 32-byte keys, `c2s` and `s2c`, generated by `scripts/gen_keys.py` and mounted read-only into containers as Docker secrets. The k6 client receives the same keys through a gitignored file.
- **Usage limit:** each process counts its encryptions and fails closed after a configured ceiling, set far below 2³² (NIST SP 800-38D, §8.3).
- **Errors:** any parse, AAD, or tag failure returns `400 {"error":"invalid_envelope"}`, with no further detail.

Replay protection *within* a route (nonce caches, timestamps) is out of scope for the minimum experiment. It is listed in the threat model as a limitation.

## 5. TLS configuration

- A local private CA and a server certificate (ECDSA P-256, SAN = service names and `localhost`) are generated by `scripts/gen_certs.sh` with OpenSSL.
- The server's `ssl.SSLContext` sets `minimum_version = TLSv1_3`. Uvicorn's default context does not enforce this, so the service builds the context itself.
- k6 trusts the private CA through `SSL_CERT_FILE`. Certificate verification is **not** disabled. `k6/bench.js` sets `minVersion: tls1.3`, but k6 v2.3 ignores that option (it logs `unknown field`). For Experiments A and B, TLS 1.3 is therefore guaranteed by the server's minimum version, and every response is checked for `tls_version == tls1.3`. `k6/infer.js` (Experiment C) uses the supported `tlsVersion: {min, max}` option as well.
- The negotiated suite, as observed, is `TLS_AES_256_GCM_SHA384`. The transport layer is therefore itself AES-256-GCM, so the `aead` configuration applies AES-256-GCM twice: once at the application layer and once in TLS records.

## 6. Measurement points

| Quantity | Source | Resolution |
|---|---|---|
| Request latency (send → last byte) | k6 `http_req_duration` | high resolution (Go timer) |
| End-to-end client iteration | k6 `iteration_duration` (encrypt + request + decrypt + integrity check) | high resolution |
| Client overhead | `iteration_duration − http_req_duration` (mean) | high resolution |
| Client encrypt / decrypt per request | `exec.instance.currentTestRunDuration` around WebCrypto calls | sub-microsecond, monotonic. The pilot used `Date.now()` (1 ms), so only its means are interpretable. |
| Client crypto cost per operation | `k6/client_crypto_bench.js`, loop of N operations | about 1 µs effective |
| Server decrypt / workload / encrypt / handler | `Server-Timing` (`perf_counter_ns`) | sub-microsecond |
| CPU, memory | Docker Engine API stats stream, cumulative counters | ~1 Hz, exact over a window |

Full per-request k6 CSV output was planned, but it was **dropped after the probe run**. The service sustains more than 10⁴ requests per second, which would produce about 10⁷ rows per 60 s run. The k6 end-of-test summary keeps every measured sample in memory, so its percentiles are exact, and it remains the primary raw per-run record.

After the pilot review (R6), a **bounded, deterministic sample** of individual requests was added. A measured request is sampled when its global iteration index (`exec.scenario.iterationInTest`) is divisible by *K*, where *K* depends on payload size (101, 25, and 3 for 1 KiB, 16 KiB, and 256 KiB). Each *K* is odd, so it is coprime with the four-item payload pool and the sample is not locked to one payload. The values are chosen to give roughly 3,000–15,000 samples per 60 s run, and a hard cap of 50,000 per run is enforced, with truncation recorded. Each sampled request contributes one line with its k6 timings, client encrypt and decrypt time, the server's `Server-Timing` stages, status, and integrity result. **The sample is not the complete request population.** It supports distributional plots and per-request breakdowns; all reported percentiles come from the k6 summary.

### 6.1 Per-run protocol (after the pilot review, R1)

1. Both API containers are recreated (`docker compose up --force-recreate --wait`). The health check runs every 250 ms during start-up.
2. A host-side probe of `/healthz` over verified TLS 1.3 must succeed for both services.
3. The resource sampler starts on the API under test, and a 2 s idle baseline is recorded.
4. k6 starts. Its warm-up (10 s in the full matrix) is unchanged and is excluded from all measurements.

`runs.csv` records each step: restart begin, healthy, and ready times; k6 launch; the k6 start time *t₀* together with the warm-up end and measurement end it implies; k6 exit; and the container ID, start time, and restart count of both API containers.

### 6.2 Open-loop run structure (Experiment B)

An open-loop run uses two consecutive k6 scenarios that share one pool of pre-allocated VUs:

| Scenario | Executor | Time | Purpose |
|---|---|---|---|
| `warmup` | `ramping-arrival-rate` | 0 → ⌈warm-up/2⌉ s: rate ramps from 0 to the target; then the target rate until 0.5 s before the warm-up ends; then a 0.5 s drain (`gracefulStop`) | Opens TLS connections and warms the server without a start-up burst. Excluded from all measurements. |
| `measure` | `constant-arrival-rate` | warm-up end → warm-up + duration | The measurement window. |

- **Dropped iterations.** k6 tags `dropped_iterations` with the scenario, so measurement-window drops are counted exactly. They must be zero. Warm-up drops are recorded and reported.
- **VU pool.** The pool is max(64, ⌈rate × 0.1 s⌉), which absorbs a 100 ms stall. An idle VU holds no connection.
- **Draining the warm-up.** The warm-up must not hard-stop in-flight iterations. With `gracefulStop: 0`, an interrupted asynchronous (aead) iteration left its VU in a state in which every later iteration on it finished without sending a request. The validation criterion r3c (iterations = requests in the measurement window) detects this.

### 6.3 Inference run structure (Experiment C, H5)

```
k6 (1 VU) ──TLS 1.3──▶ api-plain ──HTTP──▶ host.docker.internal:11434 ─▶ Ollama (Metal GPU)
          ──TLS 1.3──▶ api-aead  ──HTTP──▶            (same)           ─▶ qwen3:8b
request i: prompt p(i mod 4), mode from the 8-request cycle A B A B B A B A
```

- **Interleaving.** A single k6 VU alternates between the two API services, so both modes share the same moment of GPU and thermal state. One 8-request cycle of warm-up is followed by 48 measured requests.
- **Sampling.** Every measured request is written to the per-request log (`<run>.samples.csv`), so this experiment uses no sampling.
- **Checks around each run.** Before and after every run, the orchestrator reads Ollama's `/api/version`, `/api/tags` (digest) and `/api/ps` (residency, GPU share). It records these in `runs.csv` and aborts on a version or digest change.
- **Host sampling.** A host-side sampler records, at about 1 Hz, the Ollama processes' RSS and cumulative CPU time (`ps`), together with the GPU utilization and in-use memory counters that `ioreg` reports. Output goes to `host_resources.csv`.
- **The hop to Ollama** is plain HTTP inside the host and carries the prompt in plaintext in both modes. The model must see plaintext, so the application-layer envelope necessarily ends at the API (threat-model.md §2).

## 8. Post-hoc observability (Prometheus and Grafana)

Approved by the owner on 2026-10-20, after the core dataset's pipeline was validated. The stack is **post hoc**: it never runs during a benchmark, and `make grafana` refuses to start while a k6 container exists.

- **Why it is not live.** Live collection (k6 remote-write, cAdvisor, a Prometheus scrape loop) would add containers and client-side work to the same host and Docker VM during the measured runs. It would also change the conditions under which the pipeline was validated.
- **Export.** `analysis/export_prometheus.py` converts what is already recorded into OpenMetrics with the original timestamps: resource samples (CPU cores and working set of the API and k6 containers), run phases, exact per-run k6 statistics, the labelled 1-in-*K* request sample, the paired effect sizes from `stats.py`, and the acceptance criteria.
- **Storage.** `promtool tsdb create-blocks-from openmetrics` writes these into Prometheus TSDB blocks (backfilling).
- **Dashboards.** Prometheus (`prom/prometheus:v2.53.0`) and Grafana (`grafana/grafana:11.1.0`) are bound to 127.0.0.1. Grafana provisions two dashboards from `observability/dashboards/`:
  - *Benchmark session timeline*: run phases; API and k6 CPU and memory; sampled latency over time, as points and a heatmap.
  - *Results*: % change and the paired effect table per metric, median p50/p99, throughput and CPU per request per cell, the acceptance-criteria pass rate, and a per-run table.
- **Source of truth.** Grafana is a viewer only. Every number in the reports comes from `results/raw/` through the analysis scripts.
